# Money Intelligence: BI над операционной системой

**Автор:** Codex, ИИ-ассистент OpenAI, работающий над демо в отдельном стриме команды Дмитрия Кушникова. Мне нужен этот слой, чтобы связывать действия агента с объёмом работы, стоимостью обслуживания и обратной связью оператора. Он дополняет деревню: зритель может перейти от отдельного решения к портфелю и затем вернуться к исходному событию.

`money-intelligence.md` использован как проектная концепция. Его предложения о новых агентных модулях, cron, платежах и изменении rulebook не считались разрешением выполнить эти действия. В этом репозитории реализован самостоятельный BI-прототип; соседний репозиторий не изменялся.

## Что можно открыть

Запустить `make game-replay`, открыть <http://127.0.0.1:8787/#intelligence>. В верхней панели доступны Village и Intelligence; переключение не останавливает сценарии.

| Раздел | Что показывает |
|---|---|
| Portfolio | Счета, оценка времени сотрудников, длительность кейсов, причины holds, закрытия, таблица кейсов и покрытие данных |
| Agent activity | Реальные события запущенных в деревне записей и live-сессий: подтверждённые действия, gate denials/escalations, решения воздержаться от действия, ошибки, вызовы модели, usage, stage и checklist |
| Review queue | Детерминированные предложения с источниками, владельцем решения и формой обратной связи |
| Method & coverage | Формулы, предположения, веса, ограничения, SHA-256 источника и шаблон импорта |

Фильтр по типу кейса и ставка сотрудников пересчитывают портфель. Кнопки показателей и полосы диаграмм открывают исходные кейсы. Карточка кейса содержит номера событий, выдержки, стоимость, VAT, источник и hash набора.

## Данные: три независимых набора

**Public corpus.** Встроенный ledger воспроизводимо собран из `lettings-ops-agent/data/pm-cases-index.json`: 50 синтетических публичных кейсов, 1 505 событий, 635 индексированных вмешательств. Из них 40 — ответы владельцев, поэтому число вмешательств сотрудников равно **595**. По весам из конфигурации получается **1 325 минут**, или **22,08 часа**; при £30/час — **£662,50 расчётной стоимости**. UI округляет денежные показатели до целых фунтов; JSON сохраняет точность.

Медиана длительности — 13 дней. В 13 кейсах есть текстовые упоминания денег; ни одно из них не превращено автоматически в подтверждённый invoice. В 17 кейсах записано `CLOSED_WITHOUT_PAYMENT`, что не доказывает бесплатный ремонт: владелец мог заплатить напрямую. В корпусе есть даты будущих относительно момента сборки событий; это даты синтетического корпуса, не текущая деятельность агентства.

Денежные mentions повторяются, смешивают quote, invoice и VAT. PDF-вложения в этом BI не извлекались. У кейсов нет общих стабильных actor IDs: рейтинги подрядчиков, арендаторов и владельцев по именам не строятся. Holds показаны количеством записей; длительность ожидания из них не выдумывается.

**Portfolio lab.** Отдельная детерминированная fixture: 84 придуманных закрытых заказа за 2025 год, 6 объектов, 7 подрядчиков из mock-world. Их финансовые результаты полностью синтетические, что обозначено в UI и экспорте. Генератор намеренно создаёт превышения сметы у C-007, более низкую стоимость у C-001 и задержки согласования L-002, чтобы проверить работу правил. Это не результаты прогонов агента и не утверждения о реальных компаниях.

**Agent activity.** События текущей браузерной деревни. Live и replay считаются отдельно. Повторное воспроизведение одного baseline trace не считается новым заказом: выбирается запись с максимальным числом уже просмотренных событий. Для импортированных JSONL идентичность происхождения не заверена. Live-снимок берётся из существующего API и обновляется через SSE; переподключение обрабатывает общий reducer.

Импортированный финансовый ledger образует четвёртый, отдельный источник. Он хранится в памяти вкладки и не отправляется на сервер. Перезагрузка требует повторного импорта. SHA-256 для привязки отзывов пересчитывается по фактическому массиву jobs; hash и evidence references не заменяют независимой проверки первичных счетов.

## Расчёты и правила

Веса и пороги лежат в `demo/web/insights-rules.json`, вычисления — в `demo/web/insights-model.js`. Новых зависимостей нет.

```text
estimated_staff_cost = Σ intervention_minutes × hourly_rate / 60
effective_cost_proxy = VAT-inclusive invoice + estimated_staff_cost
adjusted_mean = (n × own_mean + 5 × matched_cohort_mean) / (n + 5)
ROI_proxy = mean(median peer cost for each job's cohort) / adjusted_mean
```

ROI здесь — отношение сопоставимой стоимости, а не финансовая доходность. Сравнение требует одинаковых `case_type` и `postcode_area`, исключает самого подрядчика из peers, требует минимум 3 собственных и 3 peer jobs для каждой работы. При недостатке данных выводится `—`. Поэтому пять из семи подрядчиков лаборатории не получают ROI: для их профессии нет другого сопоставимого поставщика.

Показан приблизительный 95% интервал среднего сырого cost: `mean ± 1.96 × sample_SD / sqrt(n)`. Малые выборки, неоднородность сложности ремонта и отличия качества ограничивают интерпретацию. Интервал не является прогнозом. Неизвестные веса времени исключают job из contractor comparison; UI отдельно сообщает об их наличии.

Invoice totals и contractor cost используют только VAT-inclusive записи. Суммы без VAT или с неизвестным VAT остаются видимыми в кейсах. Invoice/quote сравниваются только на совпадающей известной VAT-базе. Quote должен быть больше нуля. Delay cost, стоимость rework, маржа, выручка и LLM-billing не подставляются без данных. Token counters используют только model-turn input/output, не повторные status totals; cache-read показания не включены в этот счётчик.

| Правило | Условие | Предложение |
|---|---|---|
| INS-RECORD-MONEY | Есть кейсы без структурированного invoice | Заполнить денежные доказательства |
| INS-REVIEW-HOLDS | В кейсе ≥10 hold-записей | Проверить цепочку ожидания и владельца шага |
| INS-REVIEW-VARIANCE | ≥5 сопоставимых jobs; ≥25% invoice превышают accepted quote более чем на 10% | Проверить согласованные изменения объёма |
| INS-PREFERRED-REVIEW | ≥5 jobs; ROI proxy ≥1.2; rework известен для всех и ≤10% | Обсудить предпочтительный статус с владельцем |
| INS-CAP-REVIEW | ≥5 принятых quotes; ≥90% ≤£250 с VAT; median approval wait ≥3 дней | Обсудить текущий лимит согласования |

Все правила создают только карточку для человека. Неподтверждённая экономия остаётся `expected_gbp: null`. Нет tenant ranking, автоматического взыскания, пересмотра аренды или прекращения tenancy. Возраст, здоровье, состав семьи и имена не являются входами scoring. Количество сообщений само по себе не определяет ответственность арендатора.

## Обратная связь и передача агентному стриму

Оператор может принять карточку **для дальнейшего рассмотрения**, отклонить или отложить её, указав причину. Можно записать измеренный net benefit с evidence reference; он маркируется как непроверенное наблюдение человека. Отзывы привязаны к версии правил, source hash, набору кейсов и ставке расчёта. При изменении этих данных старое решение не переносится на новую рекомендацию.

Хранение — localStorage данного origin; при недоступности storage интерфейс сообщает, что данные только в памяти. **Export review packet** открывает проверяемый JSON с карточками, источниками и отзывами; можно скопировать или скачать его. `authority_granted` всегда `false`. Экспорт ничего не отправляет автоматически. Feedback packet не включает полный ledger: его можно выгрузить отдельно через Export evidence.

Контур улучшения сейчас такой:

```text
События / финансовый ledger → показатели → предложение → решение человека
     ↑                                                   ↓
новый прогон ← изменение агента после review ← JSON packet / regression case
```

Правая и нижняя части через агентную команду выполняются человеком. Автоматического обучения, записи в `rulebook_staging.md`, cron, отчётной рассылки, проверки outcome через 30/90/180 дней или вызова `create_human_task` из BI нет. Эти интеграции нужно согласовать с владельцем системы полномочий.

## Контракт импорта v1

JSON до 4 MB и 5 000 jobs. Корень: `v: 1`, `kind: "imported"`, `synthetic: boolean`, `title`, `source`, `description`, `sha256` (64 hex; при импорте пересчитывается), `jobs: []`. Самый простой шаблон — кнопка **Method & coverage → Download current ledger as an import template**.

Каждый job:

| Поле | Требование |
|---|---|
| case_id | Уникальная непустая строка |
| title, case_type, closure | Строки; closure — исходное значение статуса |
| source_ids | Непустой массив ссылок на исходные записи |
| property_id, landlord_id, tenancy_id, contractor_id | Стабильные ключи или null; не имена |
| contractor_name, postcode_area | Опциональные строки; район нужен для peer comparison |
| opened, closed | Опциональные строки дат; сохранены для контекста |
| duration_days | Число ≥0 или null; длительность импортируется, не вычисляется из неоднозначных дат |
| interventions | Массив `{kind, source_id, text}`; для отсутствующих событий — `[]` |
| hold_reasons | Объект `reason: count`, целые неотрицательные значения; либо `{}` |
| money_mentions | Массив `{amount_gbp, source_id, text}`; не используется как actual spend |
| invoice, accepted_quote | null либо `{amount_gbp, vat, source_ids}`; vat: included / excluded / unknown |
| landlord_wait_days, wait_source_ids | null либо неотрицательная длительность и непустые доказательства |
| rework, rework_source_ids | null либо boolean и непустые доказательства наблюдения за повторной работой |
| closure_refs, outcome, history_ref | Опциональные источники закрытия, текст результата и путь к истории |

`null` означает неизвестное. Ноль допустим только как записанное значение. Суммы в GBP, один job соответствует одному финансовому случаю; идентичность invoice между разными job должна контролироваться upstream. `rework: false` следует передавать только после оговорённого окна наблюдения, а не сразу после закрытия. Импорт проверяет типы и references, но не достоверность первичного учёта.

## Следующий совместный шаг

1. Добавить в финальный record внешнего агента: stable IDs, `resolution`, accepted quote, invoice с VAT/payer/evidence, время начала и конца approval wait. Согласовать adapter в этом репозитории.
2. Извлечь PDF-вложения корпуса; проверить дубликаты, scope variations, supplier IDs и VAT до формирования фактического cost ledger.
3. Вместо лабораторной fixture записать серию настоящих multi-turn agent runs с повторными stable IDs. Отдельно проверять причинность качества решений, а не только транспорт.
4. Если нужен командный review: перенести локальные отзывы в защищённое хранилище с audit log и пользователями. Для Cloudflare подойдёт отдельный Worker + D1; сейчас они не требуются и не созданы.
5. Подключить согласованный human-review inbox агента и исходы на 30/90/180 дней. Сначала доказать пользу правил, затем рассматривать прогнозирование.

## Воспроизводимость

```sh
make import-insights AGENT_ROOT=/absolute/path/to/lettings-ops-agent
make test
make build
```

Импортер читает только публичный индекс и локальный каталог. Build включает BI в тот же статический пакет и offline cache. Live API и отзывы из браузера в этот пакет не попадают. Результаты тестов и browser QA находятся в [VERIFICATION.md](VERIFICATION.md).
